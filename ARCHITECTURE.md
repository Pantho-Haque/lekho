# How lekho is built

A walkthrough of the whole project: what each piece is, why it exists, and how data flows through it.
Read top to bottom once; afterwards the per-file table at the end is enough to find things.

---

## 1. The idea in one paragraph

The reference app (honovaacademy.com, kanji) teaches a character in steps: watch the strokes animate,
trace them with numbers, trace without numbers, assemble the character from parts, then write it from
memory. Every step rests on one thing: **per-stroke centreline data for the character**. Kanji has
that for free (KanjiVG). Bengali does not. So this project is two things:

1. `bangla-strokes`: an npm package that **owns the stroke data** and the **math that compares a
   drawn stroke to a stored one**. No UI, no browser APIs.
2. `lekho` web app: a React UI that renders those strokes, collects finger input, and asks the
   package "was that right?".

The split exists because you asked for a package you can publish and reuse. Keeping all geometry in
the package also means the scoring can be unit-tested in Node without a browser.

## 3. The data model: what a "stroke" is

```ts
type Point  = [number, number];   // x, y in a 0–100 box, y grows downward
type Stroke = Point[];            // a polyline

type Direction = 'right' | 'left' | 'down' | 'up' | 'down-right' | 'down-left' | 'up-right' | 'up-left'
               | 'clockwise' | 'anticlockwise';

interface StrokeData {            // ← one authored array item
  order: number;                  // 1-based writing order (arrays are stored sorted; tests enforce order === index+1)
  direction: Direction;           // writing direction; `points` run in this direction
  points: Stroke;                 // centreline
}

interface Letter {
  char: string;        // "অ"
  name: string;        // "স্বরে অ"   (shown in the info card, spoken by 🔊)
  roman: string;       // "ô"
  group: 'vowel' | 'consonant' | 'digit';
  strokes: StrokeData[];
  parts: number[][];   // groups of stroke indices → tiles in the "build from parts" step
  hint?: string;
}
```

The package turns `StrokeData` into a **`StrokeGuide`**, which is what the app renders:

```ts
interface StrokeGuide extends StrokeData {
  index: number;    // 0-based position
  path: string;     // SVG `d` of the centreline
  start: Point; end: Point;
  label: Point;     // where the order number goes (7 units off the start, on the stroke's left side)
  angle: number;    // heading of the first segment, degrees, 0 = right, 90 = down → start arrow
  length: number;
}
getLesson(char) → { letter, strokes: StrokeGuide[], parts: PartGuide[], hasParts }
```

**`direction` is authoritative.** `orientedPoints(data)` compares the stored direction with what the
points imply; if they are opposites, the points are reversed. `getStrokes`, `matchLetter` and every
`StrokeGuide` go through it, so flipping `direction` in a data file flips the animation, the start arrow,
the hint and the scoring target together. (A disagreement that is not an exact opposite, e.g. `down` vs
`down-right`, keeps the points as stored; tests only allow same-or-opposite.)

So the app does **no stroke geometry of its own**: order, direction, number placement, arrow heading,
path strings and parts all come from the package. `scripts/annotate.mjs` converts bare point arrays into
`{ order, direction, points }` objects using `inferDirection()` (loops → clockwise/anticlockwise by signed
area; otherwise the 8-compass sector of start→end), so new letters can still be drafted as plain arrays.

Three decisions worth knowing:

- **Polylines, not SVG path strings.** An SVG `d` string would need the browser (`getPointAtLength`)
  to measure it. A point array can be measured with plain arithmetic, so the package works in Node,
  tests, workers, React Native. The app converts to `"M x y L x y …"` only at render time via
  `strokeToPath()`.
- **Fixed 0–100 box per letter.** Every letter is fitted to the same box with ~10 units of padding,
  exactly like a kanji practice card. The app's SVG uses `viewBox="0 0 100 100"`, so stored
  coordinates are rendering coordinates. Pointer input is converted back into this box with
  `getScreenCTM().inverse()`, so the learner's points and the stored points are directly comparable.
- **Constants shipped in the package, not font extraction at runtime.** Fonts give filled outlines,
  not centrelines or writing order. The vowels in `data/vowels.ts` were authored by reading
  coordinates off gridded renders of the Noto Sans Bengali outline (`scripts/glyphs.mjs`); the
  consonants and digits were drafted from the outlines by a skeletonization script and then reviewed
  by eye (§5.6). Either way the font is an authoring aid only; learners never download it.

Example, অ (4 strokes):

```ts
{
  char: 'অ', name: 'স্বরে অ', roman: 'ô', group: 'vowel',
  strokes: [
    { order: 1, direction: 'anticlockwise', points: [[15,36],[15,48],[21,59],…,[39,46]] }, // body: tip → bowl → inner curl
    { order: 2, direction: 'down-right',    points: [[59,59],[68,67],[76,75]] },           // tail into the stem foot
    { order: 3, direction: 'down',          points: [[77,25],[77,77]] },                   // stem
    { order: 4, direction: 'right',         points: [[10,25],[90,25]] },                   // মাত্রা, always last
  ],
  parts: [[0,1],[2],[3]],        // tiles: body+tail, stem, headline
}
```

## 4. The package: `bangla-strokes`

### 4.1 `geometry.ts`: pure math over point arrays

| function | purpose |
|---|---|
| `strokeLength(s)` | sum of segment lengths |
| `resample(s, n=64)` | n points spaced equally by arc length; endpoints preserved. Makes two strokes comparable point-for-point regardless of how many raw samples each had. |
| `simplify(s, ε=1.0)` | Ramer–Douglas–Peucker. Used by the editor to turn ~100 raw pointer samples into ~10 stored points. Keeps endpoints. |
| `boundingBox(strokes)` / `normalize(strokes, pad=10)` | fit arbitrary coordinates into the 0–100 box. Used by `recognize()` so input can come from any canvas size. |
| `strokeToPath(s)` | `"M x y L x y …"` for an SVG `<path d>` |

### 4.2 `score.ts`: the heuristic

`scoreStroke(input, target, tol?) → StrokeScore`

```
1. reject degenerate input (<2 points, zero length)
2. a = resample(input, 64);  b = resample(target, 64)
3. project every point of a onto b  →  index list `proj`  (see "windowed projection" below)
4. measure five things:
     startErr  = dist(a[0],  b[0])
     endErr    = dist(a[63], b[63])
     fwd       = mean over a of nearest distance to b     (input hugs the target?)
     back      = mean over b of nearest distance to a     (target is fully covered? kills scribbles on the middle)
     ratio     = len(input) / len(target)
     dirFrac   = among steps where proj changes, fraction that move forward
5. each becomes a 0–1 sub-score = 1 − err/tolerance (clamped)
6. pass       = every raw measurement within DEFAULT_TOLERANCE
   confidence = 0.35·shape + 0.25·direction + 0.15·start + 0.15·end + 0.10·length
```

```ts
DEFAULT_TOLERANCE = { start: 15, end: 15, shape: 8, shapeBack: 10, lengthMin: 0.7, lengthMax: 1.5, direction: 0.85 }
```
Units are box units; on a ~300 px card, 15 units ≈ 45 px, comfortable for a thumb. Override per call
if a letter proves fiddly: `scoreStroke(a, b, { start: 20 })`.

**Windowed projection** (`projectWindowed`). Naively snapping each input point to the globally
nearest target point breaks on loops (অ's inner curl, ঐ, ঔ): a point near the crossing can snap to
the wrong pass and the direction check sees a jump backwards. Instead:

- first input point: global nearest (so a reversed stroke correctly starts at the target's end),
- every later point: nearest within `[prev − 4, prev + 12]` samples of the previous match,
- fallback to global search if nothing in the window is within `3 × shape` units (the finger wandered off).

**Direction**. Only steps where the projected index actually changes are counted; the fraction that
move forward must be ≥ 0.85. A stroke drawn backwards produces almost all negative steps → fails,
even if its shape is perfect. (An earlier version allowed "−2 slack" per step; that let a slow
backwards trace pass, which the test `fails a reversed stroke on direction` caught. Now fixed.)

`matchLetter(input[], letter) → LetterScore` scores stroke i against stroke i (order-aware), sets
`strokeCountOk`, and scales confidence by `min(n,m)/max(n,m)` when the counts differ.

### 4.3 `recognize.ts`

`recognize(strokes, { candidates?, limit=5, normalize=true })`:
normalize input into the box → keep letters whose stroke count is within ±1 → `matchLetter` each →
sort by confidence. Deterministic, no ML. Good enough for "which vowel did I just draw"; not meant
to replace a trained recogniser.

### 4.4 `letters.ts`, `index.ts`

Thin lookups over the data arrays (`Map` by char). `index.ts` is the only entry; everything public
is re-exported there so tsup produces one bundle.

### 4.5 Build and publish

- `tsup` emits ESM (`dist/index.js`), CJS (`dist/index.cjs`), and types. `package.json#exports`
  points at them; `"sideEffects": false` lets bundlers tree-shake.
- `npm pack --dry-run` ships 8 files: dist + README + package.json.
- `prepublishOnly` runs build + tests. Publish with `npm publish -w packages/bangla-strokes --access public`.

### 4.6 Tests (`vitest`)

- `geometry.test.ts`: resample spacing, RDP keeps endpoints / collapses a straight line / keeps corners, normalize centring, path string format.
- `score.test.ts`: traced copy passes (>0.85), reversed fails on direction, offset fails on shape, mid-scribble fails, loop traced correctly passes, loop reversed fails, degenerate input, matchLetter on real data.
- `recognize.test.ts`: data sanity for all 11 vowels (points inside the box, `parts` covers each stroke exactly once), recognize returns the right letter for its own strokes, is scale/position invariant, survives jitter.

## 5. The app: `apps/web`

### 5.1 Tooling

Vite + React 19 + TypeScript + Tailwind v4 (via `@tailwindcss/vite`) + `react-router-dom`.
Theme colours live in `index.css` under `@theme` (bg, panel, cream card, ink, ghost, accent green,
active red) so Tailwind utilities like `fill-cream` and `stroke-active` exist.

`vite.config.ts` aliases `bangla-strokes` to the package **source** during `vite dev` only. That is
what makes editing `data/vowels.ts` hot-reload in the app. `vite build` uses the package's built
`dist`, exactly like a real consumer would.

### 5.2 `StrokeCanvas.tsx`: the one drawing component

Every step renders this same component with different props. It is an inline `<svg viewBox="0 0 100 100">`.

Props: `strokes: StrokeGuide[]` (from `getLesson`), `mode: 'watch' | 'trace' | 'free'`, `activeStroke`,
`completed` or `doneStrokes[]`, `showNumbers`, `showArrow`, `showGhost`, `ghostOpacity`, `playToken`,
`hintToken`, `onStroke(points)`, `shake`, `error`, `underlay`. It reads `guide.path`, `guide.label`,
`guide.order`, `guide.start` and `guide.angle`; the only geometry it computes is the live ink's path.

Layer order inside the SVG (bottom → top):

```
cream card rect + pink/red border
dashed centre guides
<underlay>                         (editor only: font outline)
ghost: all strokes, light grey, slightly wider
completed strokes: dark ink        (watch: revealed so far; trace/free: `completed` or `doneStrokes`)
watch: the stroke currently animating
trace: active stroke in red
start arrow at active.start rotated by active.angle (showArrow)
hint overlay (opacity 0 until hintToken bumps)
numbers (<text> at guide.label showing guide.order)
live ink (the finger's current polyline)
transparent <rect> LAST in DOM     ← receives all pointer events
```
Everything except the last rect has `pointer-events: none`, so the rect always wins.

**Pointer input**. On `pointerdown`: ignore non-primary pointers (palm), `setPointerCapture` (so a
finger lifting outside the card still ends the stroke), read `svg.getScreenCTM().inverse()` once and
reuse it for the whole stroke. Each `pointermove` appends a point in box coordinates (skipping moves
< 0.6 units). `pointerup` / `pointercancel` / `lostpointercapture` all finish the stroke and call
`onStroke(points)`. The `<svg>` has `touch-action: none` so the page does not scroll under the finger.

**Watch animation**. Uses the Web Animations API, not CSS transitions, because a CSS transition set
in the same frame as the dash values silently does nothing. For stroke *i*: `L = path.getTotalLength()`
(read in `useLayoutEffect`, never during render), `strokeDasharray = L`, then
`path.animate([{strokeDashoffset: L}, {strokeDashoffset: 0}], { duration: 350 + 4·L, fill: 'forwards' })`.
On `finished` → 220 ms pause → reveal it as a static dark path → start stroke *i+1*. The effect's
cleanup cancels the running animation and timer, which matters in React StrictMode (effects run twice
in dev). `prefers-reduced-motion` skips the animation and shows finished strokes.

The "hint" is the same animation played once on the red overlay path of the active stroke.

### 5.3 `Learn.tsx`: the lesson state machine

State: `stepIdx 0–5`, `strokeIdx`, `fails`, `stepDone`, `showNumbers`, `ghost`, `shake`,
`playToken`, `hintToken`, `toast`. Steps:

| # | key | canvas mode | what unlocks "এগিয়ে যাও" |
|---|---|---|---|
| 0 | watch | `watch`, numbers on, Replay button, info card | immediately |
| 1 | traceNum | `trace`, numbers + start arrow on (numbers can be hidden); counter shows the stroke's direction in Bengali | all strokes passed |
| 2 | traceNoNum | `trace`, numbers off | all strokes passed → "দারুণ! 🎉" toast |
| 3 | parts | `PartsBuilder` | Check with correct order |
| 4 | memory | `free`, no ghost | all strokes passed; a failure fades the ghost in at 35 % |
| 5 | done | ✓ + replay card | writes `localStorage["lekho.done"]` |

`onStroke(points)` is the heart:

```ts
const r = scoreStroke(points, lesson.strokes[strokeIdx].points);   // ← the package
if (r.pass) { strokeIdx++; if done → stepDone, toast }
else        { shake; fails++; if (step==='memory') ghost=true; if (fails>=3) { hintToken++; fails=0 } }
```
So the app never decides correctness itself; it only reacts to `pass`.

Header: × (back to grid), 5 progress pills, 🔊 (speech synthesis with a `bn` voice if the device
has one; silent otherwise), the target glyph. Footer: instruction text on the left, primary button on
the right, mirroring the demo.

### 5.4 `PartsBuilder.tsx`

Tiles = `letter.parts`, shuffled with a deterministic seed from the char (and never shown already in
order). Each tile is a small `StrokeCanvas` in `free` mode with `doneStrokes = that part's indices`
over a faint ghost. Tapping appends to `tapped[]` and draws those strokes dark on the big card.
**Check** compares `tapped` to `[0, 1, …]`: wrong → red border + "স্ট্রোকের ক্রম ঠিক হয়নি — রিসেট চেপে
আবার চেষ্টা করো।"; right → `onDone()` which unlocks the footer button. **Reset** clears.

### 5.5 `Home.tsx`, `lib/`

Home lists all 60 letters in three sections (স্বরবর্ণ, ব্যঞ্জনবর্ণ, সংখ্যা) as 5-column grids with a per-section
count and an overall progress bar; finished letters turn green with a ✓ (from `doneSet()`). Tapping any
letter opens its lesson; finished letters can be practised again. `Learn.tsx` drops the parts step for
single-part letters (digits, ৎ). `lib/strings.ts` holds every Bengali string in one object (`S`) plus `bn(n)` which
converts digits to Bengali numerals. `lib/progress.ts` wraps localStorage and `speechSynthesis`.

### 5.6 `Editor.tsx` (DEV only) and `scripts/glyphs.mjs`: how letters get authored

This is the content pipeline. It is never bundled in production: `main.tsx` imports it inside
`if (import.meta.env.DEV)`.

```
dev/NotoSansBengali-Regular.ttf
        │  node scripts/glyphs.mjs   (opentype.js)
        ▼
src/dev/glyphs.json        { "অ": "M… Z", … }  each outline fitted to the 0–100 box
/tmp/lekho-preview/*.svg   gridded previews (outline + current strokes + numbers) for eyeballing
        │
        ▼
/editor?c=অ                StrokeCanvas with underlay=<path d={glyph}>; you draw strokes on top
        │  onStroke → simplify(points, 1.0) → appended; reorder/delete/reverse per stroke
        │  "test" toggle switches to trace mode and prints the five sub-scores per attempt (for tuning)
        ▼
"Copy TS"                  a Letter literal → paste into packages/bangla-strokes/src/data/vowels.ts
```

The 11 vowels were produced by reading coordinates off the gridded previews and typing them, then
checking the overlay renders.

The 39 consonants and 10 digits were **generated** by `scripts/skeleton.mjs` and then reviewed:

```
outline polygons (opentype.js, fitted to the box)
  → scanline rasterize, nonzero winding, 256×256
  → Zhang-Suen thinning → 1-px skeleton
  → graph: endpoints (1 neighbour) and junction clusters (≥3) are nodes; walks between them are segments
  → prune spurs < 5 units
  → at each junction pair segments whose directions are most opposite (cos < −0.3) = one pen stroke continues
  → follow pairings into chains = strokes
  → direction: start at the end with smaller y + 0.3x (top-left first)
  → order: by leftmost x (+0.15·start y); any long horizontal near the top (মাত্রা) goes last
  → RDP simplify ε=1.0, round to 0.5
```

Every draft was rendered over its outline and inspected (`/tmp/lekho-skel/*.png`). `scripts/curate.py`
records the fixes: junk 5–8 unit connector strokes removed from প ল ষ স, dots re-added for র ড় ঢ় য় ঁ
(a solid dot thins to a single pixel and is dropped), and শ hand-authored because its two solid bowls
have no skeleton. Known limitation of the generator: strokes stop a few units short of terminal blobs,
and stroke *direction/order* is a heuristic, not a teacher's judgment; both are data edits.

### 5.7 `scripts/e2e.mjs`: end-to-end verification without a human

Launches headless Chrome with `--remote-debugging-port`, talks raw Chrome DevTools Protocol over a
WebSocket (Node's built-in `WebSocket`, no Puppeteer), emulates a 390×844 mobile viewport, and:

1. loads `/` and asserts no horizontal overflow,
2. opens `/learn/<char>`, asserts the watch title, clicks next,
3. for both trace steps: draws stroke 0 **reversed** and asserts the counter did not move, then
   draws every stored stroke through `Input.dispatchMouseEvent` (resampled to 24 points, mapped to
   screen pixels with the SVG's CTM) and asserts the counter advances and the toast appears,
4. parts: taps tiles in reverse order → asserts the error text; resets; taps in order; asserts next unlocks,
5. memory: draws all strokes, asserts completion, asserts the done screen and the localStorage entry.

It passed for all 11 vowels. Screenshots land in `/tmp/lekho-e2e/`. The script relies on two
`data-testid`s (`next`, `check`) and `data-part` attributes on tiles.

## 7. Decisions and trade-offs (why it is this way)

- **No drawing library (hanzi-writer etc.).** They expect filled outline shapes per stroke, which
  Bengali does not have. ~200 lines of SVG + WAAPI was smaller than adapting their data format.
- **Package has zero dependencies and no DOM.** That is what makes it publishable and testable;
  it forced the polyline data format.
- **One tolerance object, tuned by hand.** Thresholds were set from reasoning about thumb accuracy
  on a ~300 px card and confirmed by the e2e drawings. The editor's test mode exists precisely so
  tuning is done by looking at real sub-scores, not by guessing.
- **Per-letter box fit** rather than a shared baseline/headline across letters. ই/ঈ/উ/ঊ have tall
  ascenders; a shared scale made অ tiny. Kanji apps fit per character too.
- **Headline last** follows how Bengali handwriting is taught (body, then মাত্রা).
- **Speech synthesis, not audio files.** Zero content work; the cost is silence on desktop Chrome,
  which has no Bengali voice. Dropping `/public/audio/<char>.mp3` and preferring it is the upgrade.
- **localStorage progress, no backend.** Scope was "lesson flow only".

## 8. What is deliberately not here yet

Conjuncts (যুক্তাক্ষর) and vowel signs (কার); a recognition quiz step;
recorded audio; accounts/sync/spaced repetition; ML recognition. `recognize()` is a heuristic
ranker, adequate for a quiz among known letters, not for free-form OCR.
